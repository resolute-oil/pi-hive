Page 3 · Most important

Top 3 critical gaps

The three findings the user should decide on before any implementation begins.

G-01 — tool_call blocking is claimed but not implemented

The plan's TL;DR (§0:22) says the refactor uses Pi's tool_call blocking primitive per extension-patterns-reference.md:158-160, but F2 T2.1 only wires message_end, compaction_end, agent_settled. No task installs a tool_call handler.

The plan uses throw-to-refuse in delegate_agent.execute() — but this is the pre-dispatch equivalent, not mid-run gating. The headline Pi Best Practice is sold but not delivered.

Resolution options: (a) add F3 T3.4 wiring tool_call handler that returns block result when workerTokensRemaining <= 0, or (b) revise TL;DR to remove the claim.

Threatens: Pi Best Practices (1) Should be owned by: F3

G-04 — pauseWorkerSession exists without resumeWorkerSession

The plan introduces 6 EOL commands; the 6th (pause) has no complement, making it a dead-end. Open question #5 defaults to "all 6 commands" but lists only end/compact/respawn/pause/snapshot/restore — no resume.

This directly undermines the user's stated goal of "flexibility in EOL/respawn moments." The literal plan delivers 4 fully-wired commands (end, compact, respawn, snapshot) plus 2 partially-wired (pause, restore).

Resolution options: (a) add resumeWorkerSession(agent) as a 7th command, or (b) redefine pauseWorkerSession semantics to be auto-resumed on next prompt.

Threatens: Flexibility in EOL (3) Should be owned by: F5

G-02 — agent_settled × controller.abort ordering is not pinned

F3 T3.3 emits appendCustomEntry("budget_exhausted") and calls controller.abort(...) in the same message_end tick. If agent_settled fires immediately on abort (which it may per agent-session.d.ts:48), the agent_settled handler will write the final snapshot before the appendCustomEntry("budget_exhausted") lands — meaning the "exhausted" marker comes AFTER the "checkpoint" marker, not before.

The plan's F3 completion guard checks the abort and the emit separately but does not test that the exhausted emit precedes the checkpoint write. This is a fresh ordering dependency the plan introduces while claiming to eliminate one.

Resolution: add a test asserting "After abort-at-0%, the ledger has exhausted marker entry ID earlier in the JSONL than the checkpoint marker."

Threatens: Eliminate the bug class (4) Should be owned by: F3 + F4

Page 8 · Critical questions

Critical questions (4)

These gate the structural correctness of the refactor. Answer before implementation begins.

Q1

Should the plan implement tool_call blocking (Pi docs §5), or is throw-to-refuse in delegate_agent.execute() the only gating point?

The plan's TL;DR claims tool_call alignment but no task implements it. tool_call blocking is the documented primitive for "block an expensive call mid-run" per extension-patterns-reference.md:158-160. Without it, the plan is incomplete relative to its stated Pi Best Practices goal.

What the answer changes
If yes → add F3 T3.4 wiring tool_call handler that returns block result. If no → revise TL;DR to remove the claim.
Default if not answered
Implement tool_call blocking for bash, edit, write, read when workerTokensRemaining <= 0.
Q2

What is the resume path for pauseWorkerSession?

Pause without resume is a dead-end. The plan introduces 6 commands; the 6th (pause) has no complement. The "flexibility in EOL/respawn moments" goal requires a clear pause → resume cycle.

What the answer changes
Either (a) add resumeWorkerSession(agent) as a 7th command, or (b) redefine pauseWorkerSession semantics to be auto-resumed on next prompt.
Default if not answered
Add resumeWorkerSession as a 7th operator command (no new SDK primitive; just remove the pause marker from ledger).
Q3

How should the implementation reproduce Bug 3 to verify the structural fix?

The plan claims "Bug 3 is structurally impossible" but provides no regression test that exercises the specific symptom (runtime.* = 0 but remaining.tokens = 0 after fresh=true abort). Without such a test, the claim is unfalsifiable.

What the answer changes
Either (a) add F7 T7.7 reproducing the exact Bug 3 scenario and asserting the new ledger-based math returns correct remaining.tokens, or (b) accept that the structural fix is unverifiable and document the risk.
Default if not answered
Add T7.7 — a fresh=true delegation with budget at 99%, manual abort at 0%, then restore and assert remaining.tokens reflects actual spend.
Q4

Should agent_settled snapshot include a final getSessionStats() read or rely on the last message_end snapshot?

Per pi-sdk-session-api.md, getSessionStats() returns the full session lifetime including aborted messages. The plan uses getSessionStats() as the source. But the agent_settled handler only calls ledger.snapshot(stats, policy, "checkpoint", signal) — which writes the snapshot, but the read of stats is not specified. Is the read happening at agent_settled time, or is the snapshot just the last throttled write?

What the answer changes
If read at agent_settled → getSessionStats() includes the final abort-side usage. If relying on throttled → may miss the final state.
Default if not answered
Read getSessionStats() at agent_settled and write the result as the checkpoint.

Page 11 · Surprising

Surprising observations

Findings that didn't fit the gap inventory cleanly.

1. Plan is inconsistent on its own fourth refactor goal

The plan claims all six C1-C6 land, but the F6 task list (T6.1-T6.9) doesn't explicitly cover max-delegation-depth → depth.cap (G-18), worker-budgets → per-worker (G-19), or schema_version (G-16). The plan sells config-shape completeness but doesn't deliver it in tasks.

2. Plan is more conservative than the user's stated flexibility goal

The user wants "flexibility in EOL/respawn moments"; the plan delivers 6 commands but pause without resume (G-04) and cooperative tools not implemented (G-07). The literal plan delivers 4 fully-wired commands (end, compact, respawn, snapshot) plus 2 partially-wired (pause, restore).

3. Plan removes appendUsage from actual implementation despite listing it in TL;DR

Gap G-26 is interesting because the plan does the right thing (uses appendCustomEntry which doesn't inflate session totals) but the TL;DR still lists appendUsage as a primitive used. Future readers will be confused.

4. Plan's marker schema is internally inconsistent

Gap G-08 (3 marker values vs 6 kinds) suggests the schema was written before the 6-command EOL design. Whoever implements F5 first will hit this immediately.

5. More "How do I know" completion guards than verifiable gates

Several guards assert internal consistency (e.g., "verify session.dispose() is called") that can only be tested via spy/mocking, not via real SDK behavior. The plan's quality bar is high but its testing strategy is implementation-aware rather than behavior-aware.

6. HTML and Markdown presentations disagree on count

Gap G-15 is small but suggests the documents were not synced after a final edit. Future readers will notice.

7. Plan does not address the bug class for compaction_end-side errors

Per agent-session.d.ts:75-79, compaction_end has aborted: boolean and errorMessage? fields. The plan's F2 T2.1 wires compaction_end but doesn't check event.aborted — meaning a failed compaction triggers the recordCompaction ledger write even though no compaction happened. Bug class lurking.
