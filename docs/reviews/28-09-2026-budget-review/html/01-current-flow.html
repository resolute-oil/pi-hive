From delegate_agent invocation to the worker's first model call. The first budget check is at step 11; the worker slot is acquired at step 10. The fresh-reset path (steps 2-3) is the Bug 1 fix location.

Where Bug 1 was fixed: The reloadAgentConfig + freshResetRuntime pair (steps 2-3) was originally placed AFTER checkDispatchBudgets, so an exhausted worker could never be respawned. Commit 081380a (refined in 3be33f6) moved the pair to its current location — before every guard and before the budget check. See src/engine/dispatch.ts:213-214.

The function returns the FIRST blocking condition in declaration order. The second call at dispatch.ts:302 handles the case where queueing invalidated the budget between calls.

Mid-run — message_end

Every assistant message triggers the handler at src/engine/dispatch.ts:646-708. Three effects:

  1. Live accumulation — runtime.inputTokens += u.input etc. (read by workerConsumedTokens when status === "running").
  2. Warning at ≤20% remaining, deduped by ${scope}:${resource}:${agent|team}.
  3. Abort at 0% remaining via runController.abort(...).

Compaction — compaction_end

Debits runtime.effectiveTokens by the savings (tokensBefore - estimatedTokensAfter). Emits team_budget_recalculated. Cost is NOT recalculated.

The dual/triple counter system is the heart of the budget layer's complexity. Three counters, three write sites, three read sites.

The workerConsumedTokens choice

src/engine/governance.ts:33-58 picks one of three counters based on lifecycle:

if (runtime.status === "running") {
  return runtimeTokens(runtime, scope);  // live path
}
return runtime.governanceTokens ?? runtime.effectiveTokens ?? runtimeTokens(runtime, scope);
The bug class lives here. The ?? fallthroughs encode a state machine in source code. Every consumer has to trust the picker; tests need the fake-session pattern to exercise the transitions. The third-mystery bug is a case where the picker returns a stale frozen value after an aborted fresh run.

1.4 · fresh=true bug timeline

Three bugs in five commits. Bug 1 and Bug 2 are fixed in feat/budget-strategy at 9f950fb. Bug 3 is unresolved.

2025-09-27
Bug 1 — fresh=true doesn't reset budget FIXED
freshResetRuntime ran AFTER checkDispatchBudgets; an exhausted worker could never be respawned. Fix in commits 081380a + 3be33f6: move freshResetRuntime before every guard.
2025-09-27
Bug 2 — mid-run budget check sees stale governanceTokens FIXED
workerConsumedTokens preferred governanceTokens, which is only written at agent_end. Mid-run it was 0; worker overran by 26x. Fix in 3be33f6: return runtimeTokens(runtime, scope) when status === "running".
2025-09-28
Bug 3 — third mystery, post-test residual UNRESOLVED
After Bug 1 + Bug 2 fixes, fresh=true still aborts with tokens=0 but remaining.tokens=0. Top hypothesis: the end-of-run governanceTokens += delta accumulation at dispatch.ts:~868 reads pre-overwrite runtime.* values. Three plausible root causes ranked in ../raw-evidence/2025-09-28-fresh-true-budget-bug-unresolved.md.
Why incremental fixes haven't closed it. Three structural reasons: (1) the dual-counter system is the bug class — every counter-renaming, counter-resetting, or counter-source-changing refactor reintroduces Bug 3. (2) The end-of-run order is implicit, not explicit — the current code's sequence (stats overwrite → delta → accumulation) is correct IF getSessionStats() returns the full session-lifetime total for aborted sessions; the order is WRONG if it doesn't. (3) There is no single source of truth — even if Bug 3 is fixed, the next bug class is one step away.
