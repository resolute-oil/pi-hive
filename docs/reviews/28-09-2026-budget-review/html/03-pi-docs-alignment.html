3.1 · Three buckets

The pi-docs audit organizes patterns into three buckets: what the current code follows, what it must not violate, and what it ignores. Every quote below is from a specific doc and section anchor at /opt/homebrew/lib/node_modules/@earendil-works/pi-coding-agent/docs/.

3.2 · Patterns the current code follows

Throw to refuse an expensive tool
extensions.md#custom-tools: "Throw from execute() to produce a failed tool result. Returning an object does not mark it as an error."

The dispatch path returns { output: "Delegation blocked: ...", exitCode: 1 } for budget blocks. Equivalent to throw-to-refuse in effect.

FOLLOWED
Mode-independent behavior
extensions.md#ui-and-modes: "Keep tool and event behavior independent from rendering so non-interactive modes remain functional."

The budget layer is mode-independent. Caps apply in print, JSON, and RPC modes just as in TUI mode.

FOLLOWED
Peer dependencies with "*" ranges
packages.md: "Declare imported Pi packages in peerDependencies with a "*" range and do not bundle them."

pi-hive's package.json follows this. @earendil-works/pi-coding-agent, @earendil-works/pi-tui, and typebox are peers.

FOLLOWED
Idempotent session_shutdown
extensions.md#errors-and-cleanup: "Release resources in session_shutdown even when normal operation attempted cleanup. Keep cleanup idempotent because cancellation, reload, session replacement, and process exit can converge on the same path."

pi-hive's session_shutdown handler in src/integration/hooks.ts:496 is idempotent.

FOLLOWED
Long-lived resources from session_start, not factory
extensions.md#respect-the-runtime-lifecycle: "Do not start processes, sockets, watchers, or timers in the factory ... Start long-lived resources from session_start or from the command or tool that needs them."

The dashboard server is started in session_start. Verified in HANDOFF.md pitfall #1.

FOLLOWED

3.3 · Patterns the current code does not violate

No terminate: true unless the whole batch agrees
extensions.md#custom-tools: "Return terminate: true only when the agent should skip its automatic follow-up after every completed tool in that batch agrees to terminate."

pi-hive doesn't set terminate: true on the summarize_progress tool or any other custom tool.

NOT VIOLATED
No setActiveTools churn on every run
extensions.md#activate-tools-dynamically: "Pi records the initial prompt and tool set in the transcript's first system message ... Providers that cannot represent the transition receive a complete transcript checkpoint, which can invalidate the cached prefix."

The worker toolset is stable. Budget decisions live in tool results and event handlers, not in tool-set churn.

NOT VIOLATED
No custom() outside TUI mode
rpc-extension-ui.md: "custom() returns undefined [in RPC mode]."

No budget UI calls custom() at present (the UI is missing entirely; see Issue 4 in Report 2).

NOT VIOLATED
No ctx.shutdown() on every cap
extensions.md#errors-and-cleanup: "Use ctx.shutdown() to request an orderly process shutdown."

The budget abort uses runController.abort(...), not ctx.shutdown(). The session continues; only the in-progress turn is cancelled.

NOT VIOLATED

3.4 · Patterns the current code violates (gaps)

State in CustomEntry, not in closure CRITICAL
extensions.md#state-management: "Durable data excluded from model context → pi.appendEntry()" (which produces CustomEntry).

The cumulative counter lives in HiveState.runtimes: Map<string, AgentRuntime>, which is a closure-shaped mutable map that dies on /reload. The pi-docs-prescribed place for cumulative counters is CustomEntry with a stable customType.

Structural fix for the fresh=true bug: if the budget counter is a CustomEntry and getBranch() re-derives it on session_start, then "fresh" becomes "new session" (no entries) or "continuation" (entries present) and the distinction is enforced by the file, not by a flag that may or may not propagate.

VIOLATED
UsageEntry for worker-attributed spend HIGH
session-format.md#usageentry: "Records model-attributed usage that is not an assistant message and does not participate in LLM context ... Usage entries contribute to session token and cost totals. Pi hides them from the conversation tree."

Worker spend is summed in governanceTokens; the session file's per-message usage is not the source of truth. A redesign that does not write UsageEntry for nested worker spend is under-counting.

VIOLATED
ctx.signal propagation MEDIUM
extensions.md#events: "Use ctx.signal for nested work owned by an active turn; commands and idle session events often have no operation signal."

The mid-run message_end handler makes telemetry emits; none of them take ctx.signal. The dashboard calls from operator commands likewise. If budget enforcement is abortable on Ctrl+C, the propagation is currently incomplete.

UNCLEAR
tool_call blocking as the gate primitive MEDIUM
extensions.md#work-with-events: tool_call "can mutate input or block execution."

The current design blocks at checkDispatchBudgets in dispatchAgent (pre-session-creation), not at tool_call event time. The tool_call event would be the right place to gate a worker mid-task (e.g., to abort a worker that's still in its budget but is about to make an expensive call), but pi-hive only blocks at delegation time.

GAP

3.5 · Patterns pi documents that pi-hive currently appears to ignore

Three patterns Pi explicitly documents that the current budget code does not use. These are the structural gaps that any future redesign should address.
  1. UsageEntry for worker-attributed spend. Pi provides a built-in entry type for exactly this. If pi-hive writes a sidecar JSON file for per-worker usage instead, it is duplicating what the session file already supports.
  2. CustomEntry for cumulative counters. The fresh=true reset bug is most likely a counter that lives in closure rather than in a CustomEntry on the active branch. A redesign that uses CustomEntry removes the bug class entirely.
  3. Reload + session_start rebuild from getBranch(). Per the docs: "Reconstruct branch-sensitive state from ctx.sessionManager.getBranch() during session_start. Do not rebuild it from every file entry because abandoned branches represent alternative histories."

3.6 · Patterns that are ambiguous in Pi docs

PatternStatusImplication
Compaction details shape AMBIGUOUS Pi says details is "implementation-specific data" but doesn't prescribe a schema. The redesign can document its own shape.
UsageEntry.kind values AMBIGUOUS Pi says "Consumers should treat unknown kind values as normal usage." New kind values like "worker_call" are permission, not contract.
Ordering between extension handlers AMBIGUOUS "Handlers run in extension load and registration order." The redesign must control its load order relative to other extensions.
Branch-aware UsageEntry AMBIGUOUS Docs say usage entries "contribute to session token and cost totals" but don't say whether totals are branch-aware. May need empirical verification.

3.7 · 2026-09-28 online SDK refresh — clarifications and additions

Cross-referenced https://pi.dev/docs/latest/sdk against the locally installed /opt/homebrew/lib/node_modules/@earendil-works/pi-coding-agent/docs/ (dated Sep 22). The two are substantively identical; this section captures the four clarifications that matter for budget enforcement.

Source: Full reference with verbatim quotes is in pi-docs/extension-patterns-reference.md#12-2026-09-28-online-sdk-refresh--clarifications-and-additions.

3.7.1 steer() and followUp() return values NEW

The online docs document the return contract that local docs omit:

"steer() and followUp() expose those behaviors directly and return 'queued' if the input was queued (including after an extension transformed it), or 'handled' if an extension consumed it."

Application: a future budget feature that calls session.steer() or session.followUp() to redirect a worker mid-task (e.g., a budget-aware "switch to cheaper tools" message) must handle the queued / handled return. If an extension consumed the steered input (the rare handled case), the budget layer's subsequent assumption that "the message reached the worker" is wrong.

3.7.2 session.abort() vs session.dispose() NEW EMPHASIS

Both docs have the quotes; the online version emphasizes the distinction by putting each on its own paragraph:

"abort() stops the active operation and waits for the session to become idle. waitForIdle() waits without aborting it."
"session.dispose() aborts active work, invalidates extension contexts, disconnects from the agent, and removes event listeners. Call it when the session is no longer needed."

Three lifecycle primitives, three use cases in budget code:

PrimitiveWhat it doesUsed in budget code
runController.abort(reason) (local) Cancels in-progress run; SDK session stays alive Mid-run budget abort at 0% (src/engine/dispatch.ts:696)
session.abort() "Stops the active operation and waits for the session to become idle" Operator commands endWorkerSession, compactWorkerSession, respawnWorkerSession
session.dispose() "Aborts active work, invalidates extension contexts, disconnects from the agent, and removes event listeners" MISSING in respawnWorkerSession — see Issue 9 in Report 2

3.7.3 agent_settled vs agent_end NEW EMPHASIS

"agent_end contains the authoritative completed message. agent_end marks the end of one low-level agent run, but automatic recovery or queued work can still follow."
"Use agent_settled when the host needs to know that Pi will not continue automatically."

Application: the current agent_end handler at src/engine/dispatch.ts:707-714 does final-message text accumulation. For the budget layer's purposes — finalizing counters, emitting delegation_end, releasing the worker slot — agent_settled is more correct because any post-agent_end queued work could also consume budget. The current dispatchAgent finalization runs after session.prompt() resolves, which is close to agent_settled but not identical. Tracked as Issue 8 in Report 2.

3.7.4 session.systemPrompt is read-only CONFIRMED

"session.systemPrompt is read-only and returns the current effective system prompt, including changes that have not yet been sent to the model."

Application: the budget strategy code's emitBudgetWarning (src/engine/budget-strategy.ts:91-117) mutates runtime.systemPrompt to append the strategy hint. This is NOT a violation of the read-only session.systemPrompt contract — runtime.systemPrompt is a field on AgentRuntime (src/core/types.ts:223), not the SDK accessor. pi-hive's copy is assembled by buildWorkerPrompt and passed to session.prompt(...). The mutation never touches the SDK's read-only accessor.

If a future refactor switches to reading session.systemPrompt to inject the hint, it will fail because that accessor is read-only. The Pi-documented alternative is pi.sendMessage({...}, {triggerTurn: false, deliverAs: "followUp"}) (CustomMessage) per extensions.md#work-with-events. Tracked in current-flow/budget-check-flow.md Key observation 4.
