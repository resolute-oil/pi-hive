Executive summary

PR #57 (refactor/budget-pi-native) shipped a major v2 budget system spanning 13 features and ~2,100 LOC of rewritten code. The F10 reviewer rounds (kieran-typescript, architecture-strategist, code-simplicity) signed off on the budget module in isolation. This review asks the question the F10 rounds did not: did the features actually land and get wired into production entry points? Three parallel sub-agents audited completeness, code quality (extending F10), and the user's specific question about compact strategy.

What landed (6 of 13)

6 features are complete and wired into production. F1 (primitives), F3 (live tracking), F4 (end-of-run), F7 (race-safe accounting), F8 (reload-stable ledger), F9 (legacy cleanup), F10 (reviewer sign-off), F12 (migration guide). Wave 5A's dispatch.ts slim is also in (at 699 LOC vs the 600 target — a minor overshoot from PR #58's fresh-true fix).

Per-feature evidence in §3.

What didn't land (1 critical gap)

F5 is function-complete but unwired. The 8 operator commands, 3 cooperative tools, and the summarize_progress cooperative tool are all implemented and unit-tested but never invoked by dispatchAgent, never exposed in buildHiveTools, and never wired to any operator CLI. ~1,300 LOC + ~3,200 LOC of tests for code with zero production callers. Events.ts:195 warning tells workers to call summarize_progress({notes: "..."}) — a tool they cannot reach.

Full inventory in §4.

F2 is also unwired (parallel implementation)

The plan's F2 spine (delegateAgent) is exported and unit-tested but never called from production. The dispatch path implements the same 5-step flow inline via createWorkerSession + installWorkerBudgetHooks + runBudgetPreflight. Two paths, one test-only. docs/budgets.md describes delegateAgent as the production entry point — that's incorrect.

See §3 F2 row.

Why compact is unreachable

The compact budget strategy was intentionally deferred to v3 per plan §6.2 #12 (C5 conditional). But the deferral was never communicated to workers: the summarize_progress tool description still claims compact: true injects notes into LLM context; in practice it always returns compact_failed with details.strategy: "default". Operator-facing docs (docs/budgets.md:83) are honest about the deferral; worker-facing surfaces are not. This is dead code masquerading as a feature.

Forensic answer with 17-step evidence chain in §2.

Real bugs in the integration code

F6 wiring bug: validateBudgetsFrontmatter is exported but never called from enrichFromFrontmatter. Users writing governance: { tokenBudget: 1000 } in .md frontmatter get a silent no-op. Other 12 code-quality findings extend the F10 rounds: silent Promise rejections in events.ts:384, inconsistent error envelopes in cooperative tools, duplicated type casts, dead branches in tools.ts, operator commands that don't honor ctx.signal.

All 12 findings in §5.

The big picture

  1. The budget primitive layer is excellent. F1's BudgetLedger / BudgetPolicy / WorkerBudgetStrategy design is Pi-native, well-tested, and structurally eliminates the dual-counter bug class. The plan's "single source of truth = session.getSessionStats()" goal is achieved wherever the ledger is read.
  2. The dispatch integration is correct. runBudgetPreflight + installBudgetEventHooks wire the budget into delegate_agent end-to-end. Pre-flight, mid-run warning, tool-call block, and end-of-run ledger snapshot all work as designed.
  3. The cooperative surface is dead. 8 operator commands + 3 cooperative tools + summarize_progress total ~1,300 LOC and ~3,200 LOC of tests for code that has zero production callers. This is a 4,500-LOC deferred feature that looks shipped.
  4. The compact strategy was deferred but advertised. Users will discover dead code only when they try to use it — and they will get a confusing error. This is the highest-priority user-facing fix.
  5. Several "feature" exports are pure dead code, not features. BudgetExhaustedError class (never new'd), WorkerBudgetStrategy type with _placeholder: never (uninhabitable), EffectiveWorkerGovernance with all-undefined fields, the index.ts barrel with zero importers, the duplicated duplicated-duplicated type cast on state.config.settings. These are clearly not features per the refactor plan.

Why the compact budget strategy is unreachable

TL;DR: The compact strategy is not missing — it was intentionally deferred to v3 by plan §6.2 decision #12, but the deferral was never communicated to workers at the tool layer. The tool still advertises compact: true as a working feature; in practice it always returns compact_failed with the lie details.strategy: "compact" on the unreachable success path. This is dead code masquerading as a feature.

The decision

The plan's §2.13 C5 proposed a structured strategies config replacing the legacy flat budgetStrategy: default | compact enum. The plan explicitly marked C5 as conditional with the default recommendation "defer to v3" (refactor plan §6.2 #12):

C5 — Structured strategies (replace budget-strategy enum). Decision: conditional — land only if richer strategies are wanted in v2. Default recommendation: defer to v3.

The user accepted the default. C5 is deferred. compact as a runtime strategy is unreachable in v2.

The 17-step evidence chain

From plan to runtime, the chain that locks compact out:

Step 1 — Decision to defer

Plan §6.2 #12: "C5 — Structured strategies... Decision: conditional... Default recommendation: defer to v3."

v2 ships the C5 placeholder only. The structured-strategy shape is not implemented.

Step 2 — Type is uninhabitable

src/engine/budget/types.ts:96:

export interface WorkerBudgetStrategy { // TODO C5: deferred to v3 unless user overrides readonly _placeholder: never; }

{ readonly _placeholder: never } makes the type uninhabitable. No runtime value can satisfy it. The resolver's only legal outcome is undefined.

Step 3 — Resolver hardcodes undefined

src/engine/budget/strategy.ts:31-35:

export function resolveWorkerBudgetStrategy( _state: HiveState, _agentName: string, ): WorkerBudgetStrategy | undefined { return undefined; }

Single source-of-truth resolver returns undefined for any input. Parameters are underscore-prefixed (deliberately ignored).

Step 4 — Convenience predicates hardcode false

strategy.ts:43 (strategyRequestsWrapUp) and strategy.ts:53 (strategyRequestsCompactOnExhaustion) both return false unconditionally.

Even if a strategy object existed, the system would treat it as a no-op default.

Step 5 — Tool has its own resolver that hardcodes "default"

src/agents/tools/summarize-progress.ts:142:

function resolveStrategy(_state: HiveState, _runtime: AgentRuntime | undefined): "default" | "compact" { return "default"; }

Even though this returns a "default" | "compact" literal (not undefined), the implementation always returns "default". The docstring (lines 138-141) explicitly states: "The structured strategy (C5) is deferred to v3; for now we always return "default"".

Step 6 — Compact-mode branch always fails

summarize-progress.ts:228-251:

if (compactRequested) { const strategy = resolveStrategy(state, runtime); if (strategy !== "compact") { return { content: [{ type: "text", text: `summarize_progress: compact flag ignored under "${strategy}" strategy — operator drives intervention. Notes stored.` }], details: { ok: false, caller: callerName, reason: "compact_failed", strategy, ... }, isError: true, }; } // UNREACHABLE in v2 — strategy is never "compact" const sessionManager = runtime.session?.sessionManager; if (sessionManager?.appendCustomMessageEntry) { sessionManager.appendCustomMessageEntry("progress_note", ...); } }

When compactRequested === true, the strategy !== "compact" guard at line 231 fires, returning early. Lines 245-251 (appendCustomMessageEntry) are unreachable in v2.

Step 7 — Error message frames it as "rejected under default"

summarize-progress.ts:235: "summarize_progress: compact flag ignored under \"default\" strategy — operator drives intervention. Notes stored."

Implies the worker could in principle be on a compact strategy. That implication is false — there is no compact strategy to be on. C5 placeholder means the strategy enum is single-valued.

Step 8 — Success text lies

summarize-progress.ts:286: ${compactRequested ? " (compact honored)" : ""}

This text only executes in the success path. Since resolveStrategy always returns "default" and the guard at line 231 always fires, line 286 is reached only when compactRequested is false — the conditional append never renders.

Step 9 — Structured details also lie

summarize-progress.ts:282: const strategy = compactRequested ? "compact" : resolveStrategy(state, runtime); followed by details.strategy: strategy at line 297.

When the success path runs (only when compactRequested is false), this is fine. But the structured details would record strategy: "compact" for any compactRequested: true — except those calls always return at line 231-249 with isError: true before reaching this code. So in practice the lie never reaches the dashboard. But it's a fragile lie: if the guard order changes, the lie surfaces.

Step 10 — Tool description claims it works

summarize-progress.ts:176: "Under the compact budget strategy, pass compact: true to inject the notes into LLM context immediately; under default the flag is rejected."

The worker-facing description frames compact as a strategy toggle the user could in principle set. It does NOT say (a) no such strategy exists in v2, (b) the flag is C5-deferred, or (c) it will always be rejected in v2 regardless of configuration.

Step 11 — Schema rejects any strategies: config

src/core/schema.ts:313:

strategies: Type.Optional(Type.Never()),

A user who tries to set budgets.strategies: { on-approaching-limit: ..., on-exhaustion: ... } fails YAML validation outright. No opt-in for C5; the validator gates the v3 surface.

Step 12 — Legacy escape hatch removed

src/core/types.ts:163: "REMOVED per F9: WorkerGovernance / TeamBudgets — replaced by the new nested settings.budgets: shape. The legacy flat-key fields were deleted from config-validation's allowlist by the Wave 1B hard cutover (G-16)."

The v1 escape hatch — worker-governance.budget-strategy: compact in agent .md frontmatter — is gone. Users who upgraded and tried the legacy key get a hard-throw at config-load (G-16 hard cutover).

Step 13 — Migration guide is honest to operators

docs/budgets.md:83: "If a project still relies on compact behavior, leave it pinned to the last v1 release until C5 lands."

Operator-facing docs are honest. The deferral IS communicated — but only to operators, not to workers at runtime.

Step 14 — Operator docs explain the unreachable type

docs/budgets.md:67: "A flat default strategy is the only mode... The WorkerBudgetStrategy type carries readonly _placeholder: never, so resolveWorkerBudgetStrategy always returns undefined."

Two surfaces disagree: operator docs say no strategy exists; worker-facing tool description implies a compact strategy exists.

Step 15 — Operator command compactWorkerSession works (independent path)

src/engine/budget/worker-tools.ts:608: export async function compactWorkerSession(...): Promise<CompactWorkerSessionResult>

There IS a working operator-driven compact command — it calls session.compact(customInstructions) directly. But this is the operator path, NOT the worker-driven summarize_progress({ compact: true }). The two surfaces are independent. The cooperative path through summarize_progress is dead; the operator path through compactWorkerSession works fine.

Step 16 — F9 commit deleted the legacy budget-strategy.ts

git log refactor/budget-pi-native: e685693 refactor(budget): wave 5A — F9 legacy cleanup (delete governance.ts, budget-strategy.ts, slim dispatch.ts)

The legacy single-file budget-strategy.ts with the default | compact enum resolver was deleted in F9. The new summarize-progress.ts replaces it with a hardcoded return "default".

Step 17 — Worker-visible dashboard masks the failure

Per the cooperative-eol tests, every summarize_progress call writes a progress_notes ledger entry. The dashboard renders this as a successful wrap-up record, not as a config gap.

Operators inspecting the timeline cannot distinguish a working wrap-up from a no-op compact.

What this means for a worker

A worker (or test) that follows the tool description and calls summarize_progress({notes: "...", compact: true}) to roll its context window gets:

  • isError: true
  • Message: "summarize_progress: compact flag ignored under \"default\" strategy — operator drives intervention. Notes stored."
  • details.reason === "compact_failed"

The notes ARE stored (the tool stores them on state.progressNotes[callerName] before the strategy check), but the compact feature the worker requested is silently rejected. The (compact honored) success string and details.strategy: "compact" lie are unreachable today but would surface if the guard order changed.

Recommendations (from the compact-strategy sub-agent)

  1. Update the tool description to honestly say compact is C5-deferred. Effort: trivial.
  2. Fix the error message at line 235 — replace "compact flag ignored under ${strategy} strategy — operator drives intervention" with "compact is not implemented in this version of pi-hive (C5 placeholder); only the notes are stored." Effort: trivial.

Per plan §6.2 #5: "Operator command exposure. Decision: all 7 operator commands." But the decision says expose, not wire. The exposure is the contract; the wiring was implicit.

This is a scope gap, not a feature gap. The features are correct. The integration was never tracked.

Code quality findings (extending F10)

F10 made 3 rounds of surgical fixes on src/engine/budget/. The code-quality sub-agent verified those fixes and found 12 additional findings beyond F10.

Verified F10 fixes

  • F10 Round 1 FIND-1/2/3 (dead re-exports of THROTTLE_*, unused OperatorLedgerKind alias, unused _BudgetExhaustedError import) — all removed.
  • F10 Round 2 FIND-D1 (unused BudgetWarningDetails interface) — removed. FIND-D2 (lifecycle contract) — documented.
  • F10 Round 3 FIND-S1 (cumulativeFromRuntime missing reasoningTokens) — FIXED. worker-tools.ts:1143 now declares reasoningTokens: number and line 1146 includes it in the sum. Recommendation: add a test with non-zero reasoning tokens to pin the fix (test sets reasoningTokens: 0 today).

New findings (12)

Q1. events.ts:384 — void session.abort() without .catch (medium, error-handling)

Wraps session.abort() in try { void session.abort(); } catch {}. SDK declares session.abort(): Promise<void> (verified in node_modules/@earendil-works/pi-coding-agent/dist/core/agent-session.d.ts:419). If the SDK rejects asynchronously, this turns into an unhandledRejection. Compare with dispatch.ts:393: void session.abort?.().catch((): undefined => undefined). Recommendation: chain .catch on the abort call to match the dispatch.ts pattern.

Q2. Cooperative tools mis-classify "session missing SDK method" as "no_runtime" (medium, best-practice)

requestEndSession (worker-tools.ts:1230-1236) and requestSnapshot (worker-tools.ts:1261-1269) both return reason: "no_runtime" for two distinct cases: (a) state.runtimes.get(callerName) returned undefined, and (b) runtime's session exists but lacks the SDK method. requestCompaction correctly distinguishes these with reason: "compact_failed" + an error field. Inconsistent error envelope. Recommendation: widen RequestEndSessionResult.reason and RequestSnapshotResult.reason to "no_runtime" | "session_unavailable".

Q3. Duplicated BudgetExhaustedError handler in dispatch.ts (medium, error-handling)

Two near-identical catch blocks at dispatch.ts:161-172 (pre-slot) and :201-211 (post-slot). F10 Round 2 noted this duplication (FIND-F1) and didn't fix it. Now grown to ~14 lines each. Only delta is releaseWorkerSlot(state) in post-slot. Recommendation: extract a translateBudgetExhausted(state, runtime, caller, releaseSlot?) helper. Pass slot-release as a callback. Also drop budgetRemaining(state, runtime) from the telemetry payload on the pre-slot path — it's meaningless when the budget is exhausted.

Q4. Dead branch on effectiveWorkerGovernance().tokenBudgetScope in tools.ts (medium, best-practice)

F10 Round 3 noted that EffectiveWorkerGovernance always returns Object.freeze({}), but explicitly scoped cleanup to "consumer code, not in the budget module". tools.ts:158-160 is a consumer that branches on tokenBudgetScope === "input_output" — the "input_output" branch is unreachable. distiller.ts:140-141 and :153 have the same dead check. Recommendation: delete the unreachable branches at tools.ts:158-160 and distiller.ts:140-141,153.

Q5. state.config.settings cast duplicated 3 times (medium, type-safety)

state.config?.settings as unknown as { budgets?: ... } appears at worker-tools.ts:229-234, display.ts:87, and display.ts:94. The cast documents a real type-system seam but three copies means three places to update. Recommendation: extract a single getBudgetsConfig(state) helper that returns the cast-once value (10-line surgical change).

Q6. Silent appendCustomMessageEntry catches hide sustained failures (low, error-handling)

events.ts:372-379 (exhaustion hint), :383-390 (exhaustion abort), and :414-421 (warning hint) all wrap sessionManager.appendCustomMessageEntry in silent try/catch. A sustained failure (permission denied, disk full) means the worker never learns its budget is exhausted. Recommendation: at minimum, log the swallowed error via logRecord/emitHiveEvent.

Q7. Operator commands don't check ctx.signal.aborted before SDK calls (low, signal-propagation)

All 5 Wave 3B operator commands (endWorkerSession:578, compactWorkerSession:608, pauseWorkerSession:640, resumeWorkerSession:670, abortWorkerCompaction:706) call SDK methods that don't accept a signal parameter. If ctx.signal is already aborted, the SDK call still runs to completion. Recommendation: add early if (ctx.signal?.aborted) return { isError: true, code: "aborted", ... } at the top of each operator command.

Q8. dispatch.ts:264 silent catch on resolveModel hides legitimate failures (low, error-handling)

try { resolvedModel = resolveModel(ctx, model); } catch { resolvedModel = undefined; }. The silent catch conflates every possible resolveModel error into a generic "Cannot resolve model" message. Pattern repeated at dispatch.ts:45, 254, 402, 522. Recommendation: bind the error and log via logRecord or emitHiveEvent; include error?.message in the user-facing message for actionable diagnostics.
